Section I: Architecture & Backend Protocol
Rule 1: Enforce Strict Typing and Modern PHP
Do not write PHP 5.6 or 7.x style code. WordPress now supports modern PHP. You must enforce strict types to catch bugs early.
Directive: Every PHP file must begin with declare(strict_types=1);.
Requirement: Use return type declarations for all functions and methods.
PHP
public function get_user_count(): int {
    return 5;
}

Rule 2: Namespace Everything
Global naming conflicts are forbidden.
Directive: Never declare a class or function in the global namespace.
Format: Use Vendor\PluginName\Component.
PHP
namespace MyStudio\AwesomePlugin\Admin;

Rule 3: The "ABSPATH" Gatekeeper
Direct file access is a security vulnerability.
Directive: The very first line of executable code in every single PHP file must be:
PHP
defined( 'ABSPATH' ) || exit;

Rule 4: Sanitization Input, Escape Output
Trust no data.
Input Rule: Never accept $_POST or $_GET data without wrapping it in a sanitization function (e.g., sanitize_text_field, sanitize_email).
Output Rule: Never echo a variable without late escaping.
Wrong: echo $title;
Right: echo esc_html( $title );

Section II: The Block Editor (Gutenberg) Standards
Rule 5: The block.json Mandate
Do not enqueue block assets via PHP hooks manually.
Directive: All metadata, scripts, styles, and attributes must be defined in block.json.
Reasoning: This allows WordPress to lazy-load your assets only when the block is actually present on the page.
Rule 6: Use Native UI Components
Do not reinvent the wheel.
Directive: When building Admin or Block settings, you must use components from @wordpress/components.
Requirement: Use <TextControl>, <ToggleControl>, and <ColorPalette> instead of raw HTML <input> tags. This ensures your plugin looks native and inherits WordPress accessibility improvements.
Rule 7: Theme Integration via theme.json
Do not hardcode styles.
Directive: Your block must respect the user's theme settings.
Mechanism: Use var(--wp--preset--color--primary) and similar CSS variables generated by WordPress, rather than hardcoding hex codes like #000000.

Section III: Development Workflow
Rule 8: Standardized Tooling
Do not configure Webpack manually.
Directive: Use @wordpress/scripts.
Workflow:
npm start for development (hot reloading).
npm run build for production (minification).
Prohibited: Committing the node_modules folder to version control.
Rule 9: Automated Code Quality (Linting)
Code style is not a matter of opinion.
Directive: You must run linters before every commit.
Tools:
PHP: phpcs (PHP CodeSniffer) with WordPress Coding Standards.
JS/CSS: npm run lint:js and npm run lint:style.
Rule 10: Testing is Non-Negotiable
"It works on my machine" is not a valid test.
Directive:
Unit Tests: PHPUnit for backend logic.
E2E Tests: Playwright for ensuring the block works in the browser.

Section IV: Performance
Rule 11: Database Hygiene
Do not pollute the database.
Directive: If your plugin saves custom data, clean it up on uninstall.
Mechanism: Use a uninstall.php file to delete custom tables or options (delete_option()) when the user deletes the plugin.
Rule 12: Transient Caching
Do not run expensive operations on every page load.
Directive: If fetching external API data or running complex queries, cache the result using the Transients API (set_transient).
